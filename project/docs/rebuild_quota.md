# Phase 2.16：重建任务创建配额

`RAG4_MAX_OPEN_REBUILDS_PER_USER` 是启动时读取的正整数配置，默认 8，允许 1–10000。修改 `.env` 后应统一重启 API/worker；多个实例须配置相同上限。该值限制每位用户尚未完成的重建任务数，不限制 RAG3 上传、问答或历史版本查询。

## 状态与行为

| 状态 | 是否计入 | 原因 |
| --- | --- | --- |
| pending | 是 | 已接受、待执行 |
| running | 是 | 正在执行；仅设置 cancel_requested 仍计入 |
| failed | 是 | 可重试且保留 checkpoint；防止失败重试绕过准入 |
| ready | 否 | 执行结束，保留候选版本等待显式激活 |
| cancelled | 否 | 逻辑任务结束，保留历史、检查点和原创建键 |

新任务超限时 Python 抛出 `RebuildQuotaExceeded(ValueError)`，提供 `limit` 和 `open_count`；POST `/api/v1/index-rebuilds` 返回 429，data 只含当前用户的这两个数值，不新增任务或请求映射。没有固定 Retry-After，因为任务何时完成无法保证。创建 API 的 usage 日志记录成败及耗时，仍是尽力写入的监控日志。

同键同参数先返回原任务，即使配额已满；同键异参仍为 409。省略键或使用新键均需通过配额。首次请求仍要求源文档可读、全部 ready 及有效模型配置；文件摘要在事务锁外计算。

显式恢复将原 running 任务和 pending 续接任务在同一事务内交换，使用相同用户锁，不额外占用额度。原幂等键继续指向原任务。调低上限不会取消已有任务；超过新上限时拒绝新创建，仍允许重试、取消和恢复。

## 并发与数据安全

创建在数据库事务内先执行参数化的 `UPDATE users SET id = id WHERE id = :user_id`，再复查幂等键、统计未完成任务并插入任务及映射。InnoDB 锁定该用户行；SQLite 在读取前取得写锁，因此多个进程不依赖 Python 内存锁。原始 SQL 避免触发 ORM 的 User.updated_at 自动更新表达式。事务提交/回滚后释放锁，不在锁内读取文件或调用模型。

恢复也先锁用户，再修改任务，保持一致锁顺序。状态完成/取消只减少计数；计数直接来自任务表，不引入需维护或回填的持久化计数器。任务与请求映射写入失败整笔回滚，额度不会泄漏。

没有新增表、迁移或 Python 依赖；仍需部署此前 Phase 2 的 002–007 表结构。回退旧应用保留原任务及索引即可，配额配置不会覆盖任何数据。SQLite 的写锁会串行化不同用户的创建；MySQL 用户行锁也可能暂时阻塞该用户账号更新。锁等待超时仍沿用数据库异常处理，未新增自动数据库重试。

## 验证与限制

`tests/test_rebuild_quota.py` 覆盖超限及监控、满额幂等重放/冲突、各状态计数、历史保留、协作取消、恢复额度转移、用户隔离、并发不同键/同键、恢复与创建竞争、调低配额、事务回滚和配置边界。执行结果及合成 MySQL 并发证据见 [基线记录](../../RAG4_BASELINE.md)。

该配额是逻辑任务准入上限。它没有实现模型 Token/费用预算、单用户或全局 worker 并发槽、磁盘字节限制、ready 历史上限或索引 GC。显式恢复已取消的旧执行者仍可能完成已发出的模型调用，不能据此声称物理并发受限。已有直接单文档 job/build 入口也未套用本配额。
