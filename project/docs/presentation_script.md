我先不介绍产品，先讲一个场景。

假设你是一名研究生，导师给了你一个新课题。你做的第一件事，大概是打开知网或者

其中有三篇讲的其实是同一件事，只是换了个说法；还有两篇的结论互相矛盾，
你得再去翻它们的实验设置，搞清楚为什么矛盾。

两个星期过去了，你的文献综述还没开始写。

［停顿］

这就是今天我们要解决的问题。我叫某某某，接下来的四十分钟，我想向各位汇报的，

它做的事情很简单：**你把文献扔给它，然后用中文向它提问，它用你自己的文献回答你，

# 第二章　问题与机会

## 【P-4】信息过载：不是找不到，是找到的太多

我们先看问题的第一层。

学术研究者今天面临的困境，已经不是「找不到资料」了。恰恰相反，是资料太多。
一个稍微热门一点的方向，比如「大模型对齐」，在 arXiv 上每周新增的论文就有上百篇。
问题变成了：**在这上百篇里，哪三篇是真正和我的问题相关的？那三篇里，哪几段是
我需要读的？**

传统的关键词检索在这里彻底失效了。原因很本质：

**关键词匹配的是字符，不是语义。** 我搜「模型幻觉的缓解方法」，一篇论文通篇在讲
「如何提升生成内容的事实一致性」——它就是我要找的，但一个关键词都对不上，检索不到。
反过来，另一篇论文在相关工作里提了一句「幻觉」，它会被检索出来排在前面，
但对我毫无价值。

**关键词不理解上下文。** 「Transformer」在电力工程里是变压器，在深度学习里是一种
神经网络架构。检索系统不知道我是谁，也不知道我在做什么。

［停顿］

所以研究者的时间去哪了？大量时间不是花在思考和创新上，而是花在**筛选和验证**上。
这是一种纯粹的损耗。

## 【P-5】大模型来了，但它有三个硬伤

2022 年之后，很多人的第一反应是：那我直接问大模型不就行了？

我们必须承认大模型在语义理解上的能力是革命性的。但如果你真的用它做过学术工作，
你会很快撞上三堵墙。

**第一堵墙：知识滞后性。** 任何模型的训练数据都有截止日期。你问它上个月刚发表的
方法，它一无所知。而学术研究恰恰最关心最新进展。

**第二堵墙：幻觉。** 这是最危险的一堵墙。模型会用极其自信、极其流畅的语气，
告诉你一个根本不存在的结论，甚至编造一篇不存在的论文和它的作者。在日常闲聊中
这只是笑话，在学术场景中这是**灾难**——你可能基于一个虚构的前提，浪费三个月。

我在项目初期做过一个测试：问一个通用大模型某篇论文第 3 章的实验设置。它给了我
一段非常详细、非常合理的描述，包括数据集名称、超参数、baseline 对比。
我去核对原文——那一章根本不讲实验。全是编的。

**第三堵墙：领域与私域局限。** 你实验室内部的技术报告、你导师给的未发表手稿、
你们公司的内部资料——模型从来没见过，也不可能见过。

## 【P-6】RAG：把「记忆」换成「查阅」

那么 RAG 做了什么？

用一个类比：**纯大模型像一个闭卷考试的学生，凭记忆答题，记不清就编；
RAG 像一个开卷考试的学生，先翻书找到相关章节，再基于原文作答。**

具体到技术上，RAG 在模型生成之前，插入了一个检索环节：

1. 把用户的问题转成向量；
2. 在用户自己的资料库里，找出语义最相关的若干段落；
3. 把这些段落连同问题一起交给大模型；
4. 用系统提示词严格约束模型：**只能依据这些段落回答，资料里没有就说没有。**

三堵墙于是被同时绕开了：知识来自你刚上传的资料，所以不存在滞后；回答被约束在
给定资料内，所以幻觉被大幅遏制；资料是你私有的，所以领域局限不复存在。

**更关键的是第四点——可溯源。** 因为回答是基于具体段落生成的，我们可以精确地
告诉用户：这句话来自哪个文件的第几页。这是纯大模型永远做不到的，
也是学术场景最刚性的需求。

## 【P-7】我们的定位

所以本项目的定位是：

> **一个面向学术研究者的、私有知识库驱动的、可溯源的智能问答系统。**

三个关键词，每一个都对应一条产品红线：

**「私有知识库」**——每个用户的资料在物理层面隔离，不共享、不混淆、不泄露。

**「可溯源」**——每一条回答都必须能点开看到原文。做不到溯源的回答，宁可不给。

**「面向学术」**——宁可回答「根据现有资料无法回答该问题」，也绝不编造。
在学术场景中，一个诚实的「不知道」，价值远高于一个流畅的错误答案。

**本章一句话：传统检索不懂语义，纯大模型不可信，RAG 让模型在你自己的资料上开卷作答。**

# 第三章　产品全景（一）：普通用户视角

接下来我们完整走一遍产品。我会按照一个真实用户的使用路径来讲，
从注册开始，到得到第一个可溯源的回答为止。

## 【P-8】用户旅程总览

一个新用户的完整路径是五步：

**注册登录 → 上传文献 → 等待解析入库 → 提问 → 查看回答与引用溯源**

看起来很简单。但每一步背后都有需要认真处理的工程问题。我逐一说明。

## 【P-9】第一步：注册与登录

注册只需要邮箱和密码，**不需要验证码**。这是一个刻意的产品决策——
本系统的目标用户是研究者，注册流程每多一步，流失就多一分。

但「不要验证码」不等于「不做校验」。我们做了两件事：

**邮箱后缀白名单。** 只接受主流邮箱（outlook、qq、gmail、163、教育网等）。
这个校验前后端各做一次——前端做是为了即时反馈，体验好；后端做是因为
**前端校验永远只是体验优化，绝不是安全边界**。任何人都可以绕过前端直接调接口。

**密码规则。** 不少于 6 位。这个要求不高，但存储方式必须严格：数据库里存的是
**bcrypt 哈希**，不是明文，也不是 MD5。bcrypt 的价值在于它是慢哈希，
自带随机盐，即使数据库整体泄露，攻击者也无法用彩虹表批量还原密码。

登录成功后返回 JWT，有效期 7 天。这里有一个细节值得说：**登录失败时，
我们明确区分「邮箱未注册」和「密码错误」。**

有同学可能会问：这不是暴露了哪些邮箱注册过吗？确实。这是一个权衡。
对于一个内部使用的学术工具，**用户体验优先级高于邮箱枚举防护**——
让用户明确知道是自己记错了密码，还是压根没注册过，能省掉大量的困惑和求助。
如果这个系统要对公网开放，这一条应该改成统一提示。

［看向听众］这类权衡在系统里还有很多。我想强调的是：**它们是被想过的，
不是被忽略的。**

## 【P-10】第二步：上传文献

上传界面支持**拖拽**和**点击选择**两种方式，可以一次选多个文件。

限制是：单文件最大 50MB，单次最多 10 个，支持 PDF、DOCX、TXT、Markdown 四种格式。

这里有一个体验上的关键设计：**上传接口不等待解析完成。**

为什么？因为一个 100 页的 PDF，解析加向量化可能要几十秒；如果是扫描版需要 OCR，
可能要一两分钟。如果接口同步等待，用户会看着一个转圈的图标，
不知道系统是在工作还是已经卡死，而且浏览器还可能超时。

所以我们的做法是：**文件落盘、元数据入库之后立即返回**，状态标记为「排队中」，
真正的解析在后台线程池里进行。前端每 3 秒轮询一次状态，实时展示进度。

状态机是五个状态：`排队中 → 解析中 → 向量化中 → 已就绪 / 失败`。

用户能清楚地看到自己的文件走到哪一步了。而且——这是需求文档里一个很细致的
要求——列表里还会返回 `updated_at` 字段，也就是**状态最后更新时间**。
前端可以据此判断：如果一个文件停在「解析中」已经十分钟没动静了，
那大概率是卡住了，而不是还在正常处理。这个字段让「卡住」这件事变得可观测。

## 【P-11】第三步：文档解析——四种格式，两条路径

解析这一步是整个系统里工程细节最密集的地方。

**电子版 PDF**：用 PyMuPDF 逐页提取文本，同时记录页码。页码非常重要，
它最终会变成引用里的「第 X 页」。如果 PyMuPDF 提取效果不理想，
还有 pdfplumber 作为兜底。

**扫描版 PDF**：这是难点。扫描版本质上是一堆图片，直接提取文本会得到空白。

我们的判定逻辑是：**逐页提取文本，如果某一页的有效字符数低于阈值（当前设为 40），
就判定该页是扫描页**，把它渲染成图像，交给 OCR 引擎识别。

注意这个判定是**按页**而不是按文档的。因为现实中大量论文是混合的——
正文是电子版，但插图里的表格是扫描的。按页判定能把这种情况处理得更好。

OCR 引擎优先用 PaddleOCR，中文识别效果更好；如果服务器没装，
自动回退到 Tesseract。**如果两个都没有，系统不会崩溃，也不会假装成功**——
它会把文档标记为「失败」，并给出明确的中文提示：「该文件疑似扫描版 PDF，
但服务器未安装 OCR 引擎」。这条失败记录还会进入管理后台的失败队列，
管理员能看到。

**DOCX**：用 python-docx 提取段落，**表格内容也会被提取**并入库。
很多论文的关键数据就在表格里，漏掉表格等于漏掉最有价值的部分。

**TXT 与 Markdown**：看起来最简单，其实有个坑，我在后面「真实缺陷」那一章
会专门讲——中文编码识别，我们在这里踩了一个实实在在的雷。

Markdown 我们做了额外处理：去掉 `#`、`**` 这类排版符号，但**保留标题文字本身**，
因为标题往往是全文最凝练的语义信息，对检索质量帮助很大。

## 【P-12】第四步：切分——为什么不能整篇入库

文档解析出来之后，不能整篇直接向量化，必须切分成小块。

原因有两个。**第一，向量表达能力有限。** 把一万字压缩成一个向量，语义会被
严重稀释，检索时什么都匹配不上。**第二，大模型上下文有限且昂贵。**
我们只需要把最相关的几段送给模型，而不是整本书。

切分的核心参数是两个：**切片大小（chunk size）** 和 **重叠字符数（overlap）**。

这两个参数没有放之四海皆准的最优值——它取决于文献类型、语言、提问风格。
所以需求文档明确要求：**这两个参数必须是管理员可以在后台动态调整的**，
而不是写死在代码里。我们照做了，而且加了一条约束：**重叠必须小于切片大小**，
否则切分会陷入原地打转。这个校验在前后端各做一次。

切分策略本身也有讲究。我们不是简单地按字符数硬切，那样会把一句话从中间劈开，
两边都变得不知所云。我们采用**三级边界**：

优先在段落边界切分；段落太长就在句子边界切分（中英文标点都识别）；
遇到没有任何标点的超长文本（比如一整段代码或者化学式），才按字符硬切。

重叠的作用是防止跨块信息丢失。如果一个关键结论正好横跨两个切片的边界，
没有重叠的话两边都不完整；有了重叠，至少有一边是完整的。

## 【P-13】第五步：向量化与入库

切片完成后，调用 Embedding 模型把每个切片转成向量。我们用的是需求文档指定的
`Qwen/Qwen3-Embedding-8B`。

这里有一个**强制要求**，需求文档里标记为 [S-3]，我认为它是整个系统里最容易被
忽略、但后果最严重的一条：

> **每个向量切片写入向量库时，必须在 Metadata 中包含五个字段：
> `doc_id`、`user_id`、`file_name`、`page`、`chunk_index`。**

为什么这么重要？

因为**删除**。用户删掉一个文档时，我们必须把它对应的所有向量片段一并清除。
如果向量的 Metadata 里没有 `doc_id`，我们就**无法定位**该文档产生的向量——
它们会永远留在向量库里。

后果是什么？向量库持续积累垃圾数据，越来越大，检索越来越慢；
更严重的是，**用户以为已经删掉的文献，仍然会被检索到并出现在回答的引用里**。
这不只是性能问题，这是数据合规问题。

所以这五个字段是硬性的。删除时执行一条 `collection.delete(where={"doc_id": ...})`
就能精确清除。而且我们在自动化测试里专门写了一个用例来守护它：
上传文档、确认向量数大于 0、删除文档、断言向量数归零。

**本章一句话：从上传到就绪，每一步都要让用户看得见进度、每一个切片都要能被追溯和清除。**

# 第四章　产品全景（二）：智能问答与引用溯源

这是产品的核心。

## 【P-14】提问背后发生了什么

用户输入一个问题，点击发送。在他看到第一个字之前，系统已经完成了四件事：

**第一，问题改写。** 如果这是多轮对话中的追问——比如用户上一句问「多头注意力的
作用是什么」，这一句问「**它**在机器翻译上表现如何」——那么「它」指代什么，
向量检索是不知道的。直接拿「它在机器翻译上表现如何」去检索，
会得到一堆不相关的结果。

所以我们先调用大模型，结合前面几轮对话，把这个追问**改写成一个语义完整、
可以独立检索的查询**。改写之后大概是：「多头注意力机制在机器翻译任务上的表现」。
这样检索才有意义。

**第二，向量检索。** 把改写后的问题向量化，在**该用户专属的**向量集合里
检索出 Top-N 个候选片段，默认 N=20。

**第三，重排序精筛。** 20 个候选还是太多、太杂。我们把问题和这 20 个片段
一起交给专门的 Rerank 模型做二次打分，选出最相关的 Top-K，默认 K 取 4 到 5。

为什么要多这一步？因为向量检索用的是**双塔模型**——问题和文档分别独立编码，
再算相似度，速度快但精度有限。Rerank 用的是**交互模型**——把问题和文档拼在一起
送进模型，能捕捉细粒度的相关性，精度高但慢。

**先用快的粗筛 20 个，再用慢的精排出 4 个**，这是检索系统里非常经典的漏斗式设计，
兼顾了速度和精度。

**第四，组装提示词。** 把精排出的片段按序号编号，连同系统提示词和历史对话，
一起送给大模型。

## 【P-15】提示词：幻觉遏制的最后一道闸门

系统提示词是整个系统里最短、但可能最重要的一段文本。它的核心约束有三条：

**第一条：严格依据背景资料作答。** 不是「参考」，是「严格依据」。

**第二条：资料不足时必须明说。** 原文是：「如果资料中没有足够信息来回答问题，
请直接说明『根据现有资料无法回答该问题』，切勿编造信息。」

这一条是产品的价值底线。我们宁可让用户失望，也不能让用户被误导。
一个诚实的「我不知道」，在学术场景中的价值远高于一个流畅的错误答案。

**第三条：必须打引用标记。** 引用了哪一段，就在对应位置标上 `[1]`、`[2]`。
这些标记会被前端解析成可点击的角标。

## 【P-16】流式输出：为什么不能等

大模型生成一段完整回答需要几秒到几十秒。如果我们等它全部生成完再一次性返回，
用户会盯着一个空白页面等十几秒——这个体验是不可接受的。

所以问答接口采用 **SSE（Server-Sent Events）** 协议，**边生成边推送**。
用户在一秒之内就能看到第一个字，然后文字像打字机一样逐渐出现。

这不只是「看起来快」。心理学上，**有反馈的等待，感知时长远短于无反馈的等待**。
同样是 10 秒，流式输出的体验和空白等待的体验完全不同。

我们的 SSE 定义了四类事件：

- `chunk`：增量文本，会推很多次；
- `title`：首轮提问后自动生成的会话标题，只推一次；
- `done`：结束帧，携带完整的引用列表和消息 ID；
- `error`：出错时推送，然后关闭连接。

前端界面上还有一个「停止」按钮。用户发现问错了，可以随时中断，
不用干等模型把话说完。

## 【P-17】引用溯源：产品的灵魂

回答生成完之后，`done` 帧会带回结构化的引用列表。前端把它渲染成两种形态：

**第一种，正文里的角标。** 回答中的 `[1]`、`[2]` 被渲染成可点击的蓝色小方块。
点一下，弹窗展示对应的原文段落。

**第二种，回答下方的引用卡片。** 每张卡片显示三样东西：**文件名、位置、原文摘要**。

「位置」这里有一个细节，需求文档标记为 [I-3]：

> **PDF 文档标注「第 X 页」；TXT、Markdown 这类没有页码的文档，
> 标注「第 N 个片段」。**

这个设计很实在。PDF 有页码，用户可以直接翻到那一页去核对。TXT 没有页码，
硬编一个页码是自欺欺人，不如老实告诉用户这是第几个片段。

［停顿］

我想在这里多说一句。**引用溯源是这个产品的灵魂，不是一个附加功能。**

如果没有溯源，这个系统就退化成了一个「可能会说谎、但你查不出来」的聊天机器人。
有了溯源，用户可以用三秒钟验证任何一句话的真伪。**可验证性，
才是让一个 AI 系统在严肃场景中可用的前提。**

## 【P-18】纯模型对话模式

界面右上角有一个「知识库检索」开关。关掉它，系统就切换到**纯模型对话模式**。

这时会发生三件事：跳过向量检索、跳过 Rerank、直接调用大模型。

但有一件事**不会**变：**历史对话上下文仍然传递**。多轮对话的连贯性保持不变。

为什么要有这个模式？因为用户的需求不总是「查资料」。有时候他只是想问一句
「帮我把这段话润色一下」「解释一下什么是梯度消失」——这些问题不需要检索，
检索反而会引入噪声、拖慢速度、浪费成本。

这个模式下，`done` 帧里的 `citations` 是空数组，数据库里存的是 `NULL`。
前端不会显示任何引用卡片——因为确实没有引用，**不能假装有**。

## 【P-19】历史会话管理

每一轮对话都会持久化。左侧边栏展示历史会话列表。

**标题自动生成。** 用户提出第一个问题后，系统调用大模型生成一个 15 字以内的
摘要作为标题。比如用户问「自注意力机制的作用是什么？」，
生成的标题是「自注意力机制功能」。

这个标题通过 SSE 的 `title` 事件实时推送，侧边栏立刻更新，不需要刷新页面。

**手动重命名。** 自动生成的标题不满意？鼠标悬停在会话上，点铅笔图标，
直接改。回车保存，Esc 取消。

**模糊搜索。** 会话多了之后，顶部有搜索框，按标题模糊匹配，输入时 300 毫秒防抖。

**内容预览。** 列表里每个会话除了标题，还显示**最新一条回答的前 60 个字**。
这是需求文档 [I-2] 的要求，很实用——光看标题有时候想不起来当时聊了什么，
看一眼预览就想起来了。

**删除。** 采用逻辑删除，数据库里标记 `is_deleted=1`，便于审计追溯。

**本章一句话：改写、检索、精排、生成、溯源——五个环节，每一个都在为「可信」这两个字服务。**

# 第五章　产品全景（三）：管理后台

管理后台是给系统管理员用的，普通用户看不到入口，即使直接访问 URL 也会被拦截。

## 【P-20】用户管理

管理员可以看到全部注册用户的列表，每一行包含：邮箱、角色、状态、
**上传文档数**、最后登录时间、注册时间。

「上传文档数」这一列不是随便加的——它能让管理员一眼看出谁是活跃用户、
谁注册完就没用过，对运营决策有直接价值。

管理员可以做三件事：

**切换角色**（普通用户 ⇄ 管理员）、**启用或禁用账号**、**重置密码**。

这里有两条自我保护规则：**管理员不能取消自己的管理员角色，也不能禁用自己的账号。**
否则一个手滑就可能把整个系统锁死，没人能进后台了。这类「防呆」设计
看起来不起眼，但在生产环境里能救命。

## 【P-21】密码重置：一条完整的闭环

用户忘记密码怎么办？

本系统没有邮件服务，所以采用「**用户申请 → 管理员处理**」的人工流程。
完整闭环是这样的：

**第一步**，用户在登录页点「忘记密码」，输入注册邮箱，提交申请。

这里有一个频率限制，需求文档标记为 [M-4]：**同一邮箱 10 分钟内只能提交一次**。
如果已有未处理的申请，直接返回 400，提示「您已有待处理的申请，
请联系管理员或 10 分钟后重试」。

这个限制防止的是恶意刷单——不然有人写个脚本，几分钟就能给管理员刷出几千条
待处理申请，把后台淹掉。

**第二步**，管理员在后台看到待处理申请列表，页面顶部有醒目的黄色提示条。

**第三步**，管理员点「生成临时密码」。系统生成一个随机密码，
**只在这一次响应里显示一次**，弹窗提示管理员记录下来，关闭后无法再查看。

**第四步**，管理员通过线下渠道把临时密码交给用户。

**第五步**，用户用临时密码登录，系统提示立即修改密码。

## 【P-22】token_version：让旧令牌立刻失效

上面这个流程里，藏着一个很重要的安全机制，需求文档标记为 [S-2]。

问题是这样的：JWT 是**无状态**的。它一旦签发，在过期之前**服务端无法主动撤销**——
这是 JWT 的设计特性，也是它的软肋。

那么问题来了：假设用户的密码被盗，攻击者已经登录了，拿到了一个 7 天有效的 Token。
现在用户改了密码。攻击者手里那个 Token 呢？

**如果不做处理，它在剩下的 6 天里依然完全有效。改密码等于没改。**

我们的解法是在用户表里加一个 `token_version` 字段，默认 0。

- 签发 JWT 时，把当前的 `token_version` 写进 Token 的载荷里；
- 每次鉴权时，从数据库读出当前值，和 Token 里携带的值比对；
- **只要 Token 里的版本号小于数据库里的当前值，立刻拒绝，返回 401。**

而在两个场景下，我们把 `token_version` 加一：**管理员重置该用户密码**，
以及**用户自己修改密码**。

效果是：改密码的那一瞬间，**该用户此前签发的所有 Token，
在所有设备上，全部立即失效**。

有一个体验细节：用户自己改密码时，我们会**立刻给他签发一个新 Token**。
所以他当前这台设备不会被登出，但其他设备会。这符合直觉——
你在自己电脑上改的密码，不应该把自己踢下线。

## 【P-23】系统配置：不改代码切换模型

这是管理后台里我个人最喜欢的一块。

管理员可以在页面上直接修改：

- **大模型**：Base URL、API Key、模型名称
- **辅助任务模型**：用于问题改写和标题生成（后面会专门讲为什么需要它）
- **Embedding**：模型名称、Base URL、API Key
- **Rerank**：终结点、API Key、模型名称、Top-K
- **切片参数**：切片大小、重叠字符数
- **检索参数**：Top-N 候选数、多轮对话历史轮数上限

**改完点保存，立即全局生效，不需要重启服务。**

实现上，配置存在数据库里，应用层做了一个 5 秒 TTL 的缓存，
写入时主动失效。既避免了每次问答都查库，又保证了修改能快速生效。

这个能力的价值在于：**从 DeepSeek 换到通义千问，从云端模型换到本地部署的模型，
不需要改一行代码，不需要重新发布，在后台改个地址就行。**
需求文档里「模型层抽象」这条要求，落到实处就是这个页面。

## 【P-24】API Key 的三重保护

配置里涉及 API Key，这是敏感信息。需求文档 [S-1] 对它有严格要求，
我们做了三重保护：

**第一重，静态加密。** Key 在写入数据库之前，先用 **AES-256-GCM** 加密，
数据库里存的是密文，前缀是 `enc::v1::`。即使数据库被拖库，
攻击者拿到的也只是一串密文。

选 GCM 模式是因为它同时提供**加密和完整性校验**——密文被篡改时解密会直接失败，
而不是解出一段垃圾数据。

**第二重，响应脱敏。** 管理后台读取配置的接口，**永远不返回明文**，
只返回掩码，比如 `sk-****fkdn`。我们专门写了一个测试用例，
断言整个 HTTP 响应体里不包含明文 Key。

**第三重，留空即不修改。** 前端的 Key 输入框永远是空的，
占位符显示当前掩码。管理员如果只是想改模型名称，不用重新输入 Key——
留空就表示「保持原值」。

这一条看起来是体验优化，实际上是**防止误操作清空线上密钥**。
如果留空表示「清空」，那管理员改个模型名就可能把整个系统的大模型调用打挂。

## 【P-25】运行监控

后台第三个模块是运行监控，数据来自 `usage_logs` 表。

系统会记录每一次外部调用：大模型、Rerank、OCR、向量检索、Embedding。
每条记录包含事件类型、耗时、Token 消耗、成败、错误摘要。

监控页面展示八个核心指标：大模型调用次数、Token 消耗量、Rerank 调用次数、
向量检索次数、OCR 处理次数、总调用次数、失败次数、失败率。

下面是**每日调用趋势图**，用纯 CSS 实现，没有引入任何图表库——
为了一个柱状图引入几百 KB 的依赖不划算。

最下面是**失败队列**，列出解析失败的文档：文件名、失败原因、时间、文档 ID。
管理员能直接看到「哪个用户的哪个文件因为什么原因失败了」，
而不是只看到一个冷冰冰的失败计数。

**本章一句话：后台不是给开发者用的调试面板，是给运维人员用的控制台——
每一个功能都对应一个真实的运维动作。**

# 第六章　技术架构

## 【P-26】整体架构：四层

系统分为四层，自上而下：

**第一层，前端。** React 18 + TypeScript + Vite + TailwindCSS。单页应用，
响应式布局，桌面端和手机端共用一套代码。

**第二层，后端应用。** Python 3.10+ 与 FastAPI。选 FastAPI 有三个理由：
原生支持异步、自动生成 OpenAPI 文档、Pydantic 带来的请求校验几乎零成本。
后端内部按职责划分为 core（基础设施）、models（数据模型）、schemas（校验）、
api（路由）、services（业务与 RAG 编排）、utils（工具）六个包。

**第三层，数据存储。** 三种存储各司其职：

- **MySQL 8** 存结构化数据：用户、会话、消息、文档元数据、系统配置、运行日志；
- **Chroma** 存向量：每个用户一个独立集合；
- **本地文件系统**存原始文件：按 `user_id` 分目录。

**第四层，外部服务。** 大模型 API、Embedding API、Rerank API，
全部走 OpenAI 兼容协议，可在后台随时替换。

## 【P-27】为什么这么选：几个关键决策

**为什么用 Chroma 而不是 Milvus 或 Qdrant？**

因为本项目的数据规模——单用户几十到几百篇文献——完全在 Chroma 的舒适区内。
Chroma 是嵌入式的，不需要独立部署和运维，本地持久化，
对一个学术工具来说复杂度刚好。

但我们做了一层**向量库抽象**。所有向量操作都收敛在 `BaseVectorStore` 接口后面：
`add`、`search`、`delete_document`、`drop_user`、`count`。
Chroma 只是其中一个实现。将来数据量涨上来要迁移到 Milvus，
只需要新增一个实现类，**上层业务代码一行都不用改**。

这个抽象还带来一个意外的好处：我们顺手写了一个纯 Python 的兜底实现
`LocalVectorStore`，用 JSON 持久化，余弦相似度暴力检索。
在没有安装 chromadb 的环境里，系统能自动降级到它，功能完整可用。
这让整个项目的「开箱即跑」门槛降到了最低。

**为什么用同步 SQLAlchemy 而不是异步？**

这是一个被认真权衡过的决定。异步 ORM 在高并发下有优势，但它会让整个代码库
染上 `async/await`，调试复杂度显著上升。而本项目的性能瓶颈**根本不在数据库**——
在外部 API 调用上，一次大模型生成要 8 秒，数据库查询是毫秒级。

FastAPI 会把同步的路由函数自动放到线程池里执行，不会阻塞事件循环。
所以我们选择了同步 SQLAlchemy：**代码更直白，调试更容易，
而性能上没有任何实际损失。**

**为什么 SSE 而不是 WebSocket？**

问答场景是**单向推送**——服务端往客户端推文字，客户端不需要在流中反向发消息。
SSE 天然适合这个场景，它基于普通 HTTP，不需要协议升级，
断线自动重连，经过反向代理时的坑也少得多。WebSocket 是全双工的，
在这里属于杀鸡用牛刀。

## 【P-28】RAG 引擎：六个环节

RAG 引擎是系统的核心，由六个服务模块串联而成：

**1. 解析（parser_service）**：多格式解析，扫描版判定，字符集识别。
**2. 切分（chunking_service）**：三级边界切分，重叠控制。
**3. 向量化（embedding_service）**：批量调用 Embedding API，批大小 16。
**4. 存储与检索（vector_store）**：用户级隔离的向量读写。
**5. 精排（rerank_service）**：云端 Rerank，超时自动降级。
**6. 生成（llm_service + rag_service）**：提示词组装、流式生成、引用构造。

每个模块职责单一，之间通过明确的数据结构传递（`TextBlock`、`Chunk`、
`VectorRecord`、`RetrievedChunk`），没有隐式耦合。

这样做的收益在真实联调时体现得淋漓尽致：当我们发现 Rerank 的模型名写错了，
**修改只涉及一个文件的一行**；当我们发现需要给辅助任务单独配模型，
**改动集中在 llm_service 的一个参数上**。

## 【P-29】三级超时降级：让系统不会整体失败

需求文档 [M-6] 定义了三条降级策略，我认为这是整份文档里最有工程素养的一段：

| 环节 | 超时阈值 | 降级行为 |
|------|----------|----------|
| 问题改写 | 3 秒 | 用原始问题直接检索，**SSE 连接不中断** |
| Rerank 精排 | 3 秒 | 跳过精排，直接用向量检索的 Top-K，`done` 帧携带 `rerank_timeout` 警告 |
| 大模型生成 | 30 秒 | 推送 `error` 事件并关闭连接，提示用户重试 |

这三条背后是同一个设计哲学：**辅助环节的失败，不应该导致主流程的失败。**

问题改写失败了？那就用原问题检索，效果差一点，但用户依然能得到答案。
Rerank 挂了？那就用向量检索的结果，精度低一点，但用户依然能得到答案。

**只有大模型本身失败时，我们才承认这一轮问答失败**——因为没有它就没有答案，
这是不可降级的核心依赖。

而且降级不是静默的。Rerank 降级时，`done` 帧会带上 `warnings: ["rerank_timeout"]`，
前端渲染成一条黄色提示：「云端精排服务超时，本次已直接使用向量检索结果」。
**用户知道这次结果的质量可能打了折扣**——透明比假装正常更重要。

## 【P-30】数据隔离：三个层次

多用户系统里，最不能出错的就是数据隔离。我们做了三层：

**第一层，物理文件隔离。** 每个用户的文件存在 `{上传目录}/{user_id}/` 下。

这里有个安全细节：**落盘时的文件名用的是系统生成的 `doc_id`，不是用户上传的
原始文件名。** 原始文件名只存在数据库里用于展示。

为什么？因为用户上传的文件名是**不可信输入**。如果直接用它拼路径，
一个名为 `../../../etc/passwd` 的文件就可能造成路径穿越。
用 `doc_id` 命名，从根本上消除了这个风险，顺便还解决了重名覆盖问题。

**第二层，向量物理隔离。** 这是需求文档的强制要求：
**每个用户在 Chroma 里拥有独立的 Collection**，命名规则 `col_user_{user_id}`。

注意这是**物理隔离**，不是「查询时加个 user_id 过滤条件」的逻辑隔离。
逻辑隔离依赖每一次查询都不写错过滤条件——只要有一个地方漏了，
就是跨用户数据泄露。而物理隔离下，检索时打开的**就是自己的集合**，
别人的数据在物理层面就不在检索范围内。

**第三层，关系库隔离。** 所有查询强制附加 `user_id` 条件。

这里还有一个刻意的设计：**越权访问返回 404，而不是 403。**

区别在哪？403 等于告诉攻击者「这个资源存在，只是你没权限」——
这本身就是信息泄露，攻击者可以用它来枚举系统里有哪些文档 ID。
404 则是「这个资源不存在」，攻击者什么也得不到。

## 【P-31】一个容易被忽略的时序问题

我想讲一个开发过程中发现的、很有代表性的技术细节。

问题是这样的：一问一答两条消息，在列表里显示的时候顺序颠倒了——
先显示回答，再显示问题。

排查下来，根因在数据库：**MySQL 的 `DATETIME` 类型默认只精确到秒**。
一问一答往往在同一秒内写入，两条记录的 `created_at` 完全相同。
按时间排序时，数据库返回的顺序是**不确定的**。

而消息 ID 是 UUID，随机的，拿它做次级排序键毫无意义。

有几种解法。改字段类型加毫秒精度？要改 DDL，而 DDL 是给定的规格。
在应用层维护一个序号？要加字段，同样动 DDL。

我们的解法是：**让 ID 本身按时间单调递增。**

消息 ID 改成「纳秒时间戳的十六进制 + 随机后缀」的格式，
并且用一个锁保证纳秒值严格单调（防止同一时刻并发生成重复前缀）。
这样 `ORDER BY created_at, id` 就能得到稳定且正确的时序，
**一行 DDL 都不用改。**

［停顿］

我讲这个案例，不是因为它多难，而是因为它很典型：
**很多严重的线上问题，根因都藏在这种"看起来不可能出错"的地方。**
而发现它的唯一方式，就是真的把系统跑起来，看真实的数据。

**本章一句话：好的架构不是选了多时髦的技术，是每个选择都有理由，每个抽象都有它要应对的变化。**

## 【P-32】测试体系

后端有 77 个自动化测试用例，分为五个文件：

| 文件 | 用例数 | 覆盖内容 |
|------|--------|----------|
| `test_auth.py` | 12 | 注册校验、登录提示区分、JWT 鉴权、重置频率限制、token_version 失效 |

不需要 MySQL——测试用 SQLite 临时库；不需要向量库服务——Chroma 是嵌入式的；

意义是什么？**任何人克隆代码之后，敲一个 `pytest` 就能验证系统是否完好，
不需要任何前置配置。** 这对项目的可维护性、对交接给下一个人，价值巨大。

其中 Mock 的 Embedding 用的是字符 n-gram 哈希，特点是**确定性**——
相同文本永远得到相同向量，相似文本的余弦相似度也接近。
所以连「上传文档 → 检索 → 命中正确片段」这样的完整链路都能在离线状态下测通。

## 【P-33】但是——测试全绿，不等于系统能用

［停顿，加重语气］

77 个用例全部通过的那一刻，说实话，我以为项目做完了。

然后我做了两件事：**用真实浏览器把产品完整用了一遍，
用真实的大模型 API 把链路完整跑了一遍。**

结果发现了 **7 个真实缺陷**。其中至少两个，严重到会让用户认为「这个产品是坏的」。

我把它们全部列在这里，因为我认为**这 7 个缺陷比 77 个通过的用例更有价值**——
它们说明了自动化测试的边界在哪里。

## 【P-34】第一轮：浏览器实测，3 个缺陷

**缺陷 1（严重）：用户提出的第一个问题，回答根本不显示。**

现象：在「新对话」状态下提问，问题上去了，然后……什么都没有。
界面一片空白。但如果刷新页面，或者切换到别的会话再切回来，
回答又完整地出现了。

根因：前端在「新对话」状态下提问时，会先创建会话，然后跳转路由到
`/chat/{会话ID}`。路由参数一变，加载历史消息的副作用就重新触发，
去服务端拉取消息列表。而那一瞬间，助手的回答还没生成完、还没落库，
**拉回来的数据把本地正在流式渲染的占位气泡覆盖掉了**。
后续的流式文本找不到目标消息，就再也渲染不出来了。

注意：**后端行为完全正确，数据也正确入库了。** 坏的是前端的状态时序。
77 个后端测试用例，一个都不可能发现它。

修复：用一个引用标记「本地已持有消息的会话」，跳过这次多余的拉取；
同时补上切换会话时中断上一个未完成流式连接的逻辑。

**缺陷 2：运行监控的柱状图高度为 0。**

现象：图表区域有数字、有日期，就是没有柱子。

根因：父容器用了 `items-end`，导致各列高度塌缩成内容高度，
柱体的百分比高度失去了参照基准。

这是纯 CSS 问题。任何后端测试、任何类型检查都发现不了，
**只有用眼睛看渲染结果才能发现。**

**缺陷 3：控制台两个 404。** 缺 favicon。小问题，但一个专业的产品不该有
控制台报错。补了一个内联 SVG 图标。

## 【P-35】第二轮：真实大模型联调，4 个缺陷

这一轮更有价值，因为它们全都是「按文档实现是对的，但接上真实模型就不可用」。

**缺陷 4：Rerank 模型名硬编码，换服务商必然失败。**

需求文档只要求管理员可配置 Rerank 的终结点、Key 和 Top-K，没提模型名。
我按文档实现，模型名写死成了 Cohere 的取值 `rerank-multilingual-v3.0`。

接上硅基流动一测——精排从来没成功过。因为硅基流动用的是
`BAAI/bge-reranker-v2-m3`，模型名对不上，请求直接被拒。

**更隐蔽的是：这个失败被降级逻辑静默吞掉了。** 我们的降级设计是
「Rerank 失败就用向量检索结果」，所以从用户视角看，问答一切正常，
只是精度差一点。如果不去翻运行日志，**这个问题可以潜伏很久**。

修复：新增 `rerank.model` 配置项。

**缺陷 5：回答被截断，甚至完全为空。**

现象：连续问同一个问题，有时候回答完整，有时候只输出二十几个字就断了，
有一次干脆一个字都没有。

根因：`deepseek-ai/DeepSeek-V4-Flash` 是**推理型模型**——
它在给出答案之前，会先输出一段「思考内容」（`reasoning_content`）。
而这段思考内容**同样计入输出预算 `max_tokens`**。

我们没有显式设置 `max_tokens`，用的是服务商默认值（常见是 512）。
思考过程一长，预算就被吃光了，正文自然被截断。

修复：主生成显式设置 `max_tokens=4096`。

**缺陷 6：标题生成与主回答流并发，触发限流把主流掐断。**

现象：回答只输出 25 个字就断了，而且断点**紧跟在 `title` 事件之后**。

根因：为了让标题尽快显示，我把标题生成放在了一个独立线程里，
与主回答流**并发**执行。两个请求用的是同一个 API Key，
触发了服务商的并发限制，主回答流被服务端提前关闭。

修复：改成主回答流结束后再顺序生成标题。接口文档允许标题在
「文本传输期间**或即将结束时**」推送，所以这个改动仍然合规。

**缺陷 7（最有价值）：推理型模型让问题改写和标题生成必然超时。**

这一条不是 bug，是**设计缺口**。

需求文档规定：问题改写超时阈值 3 秒，超时就降级用原问题。
标题生成也有类似的时间预算。这个设定在文档写作时是合理的——
那时候的模型生成一句短文本就是一两秒的事。

但现在的主流模型是推理型的。我做了一个实测，同一条「生成 15 字标题」的请求：

| 模型 | 耗时 |
|------|------|
| `deepseek-ai/DeepSeek-V4-Flash`（推理型） | **19.9 秒** |
| `Qwen/Qwen3-VL-8B-Instruct`（指令型） | **1.8 秒** |

**相差 11 倍。**

后果是：问题改写每次都超时降级，多轮追问里的「它」「这个方法」永远得不到正确解析；
标题生成每次都超时，标题永远退化成问题的前 15 个字。

**功能没有中断——降级逻辑正确地工作了。但这两个功能实际上形同虚设。**

［停顿］

修复方案是新增一个 `llm.aux_model` 配置项：**主回答仍用大模型保证质量，
问题改写和标题生成交给一个小的指令型模型**。留空则复用主模型，
行为与之前完全一致，向后兼容。

配置之后的实测数据：

| 环节 | 修复前 | 修复后 |
|------|--------|--------|
| 问题改写 | 4.5 秒（超时降级） | **2.4 秒（成功）** |
| 标题生成 | 11.4 秒（超时降级） | **2.1 秒（成功）** |

标题也终于是真实生成的了——「自注意力机制功能」「切片大小对检索的影响」，
而不是问题的前 15 个字。顺带还降低了这两项的调用成本。

## 【P-36】这 7 个缺陷告诉我们什么

［看向听众］

我想用一页来总结这件事，因为我觉得它比任何功能列表都重要。

**第一，自动化测试守护的是「逻辑正确」，守护不了「体验可用」。**
缺陷 1 里后端逻辑完全正确、数据完全正确，坏的是前端的状态时序。
缺陷 2 是纯 CSS 渲染问题。这两类问题，**只能靠真的把产品用一遍来发现**。

**第二，Mock 守护的是「流程贯通」，守护不了「真实世界的复杂度」。**
Mock 的模型永远秒回、永远返回规整的格式、永远不限流。
而真实模型会思考 20 秒、会先吐一段思考内容、会限流、会截断。
**缺陷 4 到 7，全部只能在真实 API 上暴露。**

**第三，需求文档也会过时。** 缺陷 7 里的 3 秒超时预算，在文档写作时是合理的，
在推理模型普及后就不再成立了。**实现者的责任不是机械地照抄文档，
而是在发现文档与现实脱节时，提出并落实修正方案。**

所以我们的结论是：**一个系统的验收标准，应该是「测试通过 + 浏览器实测 + 真实依赖联调」
三重验证，缺一不可。**

为了让这件事可持续，我们把浏览器验证也固化成了脚本——
`frontend/e2e/smoke.mjs`，一条命令跑完整旅程：
注册、登录、上传、等待就绪、流式问答、点击引用、管理后台三个页面、
移动端响应式，共 10 个节点，全程截图。这次的前 3 个缺陷就是它抓到的。

**本章一句话：测试全绿只是及格线，真的跑起来才是交付线。**

# 第八章　性能实测

## 【P-37】真实链路耗时

这是用真实 API 跑出来的分环节耗时，全部来自 `usage_logs` 表的真实记录：

| 环节 | 使用模型 | 实测耗时 |
|------|----------|----------|
| 文本向量化 | `Qwen/Qwen3-Embedding-8B` | 2.3 秒 |
| 向量检索 | Chroma（含向量化） | 2.4 秒 |
| 云端精排 | `BAAI/bge-reranker-v2-m3` | 1.9 秒 |
| 问题改写 | `Qwen/Qwen3-VL-8B-Instruct` | 2.4 秒 |
| 标题生成 | 同上 | 2.1 秒 |
| 大模型生成 | `deepseek-ai/DeepSeek-V4-Flash` | 8.5 秒 |

文档处理侧：一份 3 页 PDF 加一份中文 Markdown，从上传到全部「已就绪」，
**耗时约 6 秒**，远优于需求文档「100 页以内 30 秒」的指标。

## 【P-38】关于检索时延指标，我要说一句实话

［停顿，语气认真］

需求文档规定：**语义检索 + 云端 Rerank（不含大模型生成）端到端应在 2 秒以内。**

我们当前的实测是：**向量检索 2.4 秒 + Rerank 1.9 秒 ≈ 4.3 秒。**

**这个指标目前没有达标。** 我认为如实说明比粉饰过去更重要。

原因分析，主要是三个：

**第一，网络往返是大头。** 当前的测试环境在容器内，出网要经过一层代理，
到硅基流动的服务器还有公网往返。**Embedding 调用本身 2.3 秒里，
绝大部分是网络时间，不是计算时间。** 部署到与模型服务同区域的云服务器上，
这一项预计能降到几百毫秒。

**第二，Embedding 走的是云端 API。** 每次提问都要发一次 HTTP 请求。
如果换成本地部署的小型 Embedding 模型（比如 bge-small），
向量化可以降到几十毫秒，代价是需要一张显卡。

**第三，Rerank 也是云端调用。** 同理。

**优化路径**已经很清晰，按性价比排序：

1. **同区域部署**——零代码改动，预计收益最大；
2. **本地 Embedding 模型**——需要 GPU，但能把向量化压到毫秒级；
3. **查询向量缓存**——重复或相似问题直接命中缓存；
4. **Top-N 调优**——当前 N=20，降到 10 能减少 Rerank 的输入量。

我想强调的是：**这个数字是可测量、可归因、可优化的**，
因为我们把每一次外部调用的耗时都记进了 `usage_logs`。
管理后台的运行监控页面上，随时可以看到每个环节的真实耗时分布。
**能被测量的问题，才是能被解决的问题。**

## 【P-39】并发能力

需求文档要求支持至少 10 个并发用户同时提问。

我们的架构支持这一点：文档解析在独立线程池里（默认 4 个 worker，可配置），
不阻塞问答；问答走 SSE 流式，每个连接占用一个线程；
数据库连接池默认 10 个连接、最大溢出 20。

生产部署建议用 Gunicorn 起 4 个 Uvicorn worker，配合 Nginx 反向代理。
需要特别注意的是 **Nginx 必须关闭对 `/api/` 的缓冲**（`proxy_buffering off`），
否则 SSE 的增量文本会被 Nginx 攒着不发，流式效果完全失效——
用户会等很久然后一次性看到全部文字。这个坑我们在部署文档里写清楚了。

**本章一句话：性能数据必须真实，不达标就说不达标，但要说清楚为什么、怎么优化。**

# 第九章　现场演示

## 【P-40】演示脚本

接下来我用大约 8 分钟做现场演示。演示环境已经接入真实的大模型服务。

**第一步，注册与登录（30 秒）。**
新建一个账号，展示邮箱后缀校验——我故意输入一个不支持的后缀，
大家会看到明确的中文提示。然后正常注册、登录。

**第二步，上传文献（1 分钟）。**
拖拽两个文件进去：一份 3 页的英文 PDF 论文，一份中文 Markdown 笔记。
大家会看到上传进度条，然后状态从「排队中」变成「解析中」、
「向量化中」，最后变成绿色的「已就绪」。整个过程大约 6 秒。

**第三步，第一次提问（2 分钟）。**
我问：「多头注意力的作用是什么？论文里用了几个注意力头？」

请注意三件事：
- 回答是**逐字出现**的，不是等待后一次性显示；
- 侧边栏的会话标题在过程中**自动变成了**「多头注意力作用与头数」；
- 回答里有蓝色的 `[1]` 角标，下方有引用卡片。

**第四步，验证溯源（1 分钟）。**
点击引用卡片，弹窗显示原文段落，标注「第 2 页」。
我们可以对照 PDF 原文——**第 2 页确实写着 h = 8**。
回答准确，引用精确。

**第五步，多轮追问（1.5 分钟）。**
我接着问：「那**它**在机器翻译任务上取得了什么成绩？」

注意这句话里的「它」。系统会先做问题改写，把它还原成完整查询，
然后检索到 PDF 的第 3 页，答出 BLEU 28.4 和 41.0 这两个具体数字。
**代词被正确解析了。**

**第六步，中文文档与片段引用（1 分钟）。**
换个问题问中文 Markdown：「切片大小对检索质量有什么影响？」
注意这次的引用标注是「**第 1 个片段**」而不是页码——
因为 Markdown 没有页码，系统如实标注片段序号。

**第七步，管理后台（1.5 分钟）。**
切换到管理员账号，展示三个页面：
- **用户管理**：可以看到刚注册的账号和它的文档数；
- **系统配置**：API Key 显示为 `sk-****fkdn` 掩码，明文永不返回；
- **运行监控**：刚才这几次提问产生的调用次数、Token 消耗、
  每个环节的真实耗时，全部在这里。

**第八步，响应式（30 秒）。**
把浏览器窗口拖窄，或者用手机扫码打开——布局自动切换成移动端形态，
侧边栏变成抽屉式导航。

## 【P-41】演示中的应急预案

［这一页只讲给自己听，现场不展示］

如果演示出问题，按以下顺序处理：

- **网络不通 / API 超时**：切换到离线 Mock 模式（`DEV_MOCK_AI=true`），
  全链路依然可以完整演示，只是回答内容是模板。提前准备好一个已跑通的
  录屏作为最后兜底。
- **上传后长时间不就绪**：说明 Embedding API 异常。直接切到已经准备好的
  预置账号，里面有提前上传好的文档。
- **回答生成很慢**：这是真实情况，不要慌。可以顺势讲解流式输出的价值，
  以及运行监控里能看到的耗时分布。
- **被问到不会的问题**：诚实回答「这一点我们还没有验证，
  会后我补充数据给您」。**不要编造**——这和产品本身的价值观是一致的。

# 第十章　项目价值与展望

## 【P-42】三重价值

**第一重，直接的使用价值。**
对研究者而言，它把「读几十篇文献找一句话」压缩成「问一句话，
拿到带出处的答案」。而且因为可溯源，这个答案是**可验证**的，
可以直接用于学术工作。

**第二重，技术架构的可迁移价值。**
这套架构——文档解析、切分、向量化、检索、精排、生成、溯源——
**不是学术专用的**。把知识库换成企业内部文档，它就是企业知识管理系统；
换成法律条文和判例，它就是法律检索助手；换成产品手册和工单，
它就是智能客服。

因为我们做了模型层和向量库层的抽象，迁移成本非常低。

**第三重，工程方法论的价值。**
这个项目最值得沉淀的，可能不是代码，而是那套「三重验证」的方法：
**自动化测试 + 浏览器实测 + 真实依赖联调**。
以及那 7 个缺陷背后的教训——它们对任何一个要交付到生产环境的 AI 系统都适用。

## 【P-43】后续规划

**短期（1–2 个月）：**
- 性能优化，把检索链路压到 2 秒以内，达成需求文档指标；
- 补齐前端自动化测试（当前只有端到端冒烟脚本）；
- 支持更多格式：PPTX、HTML、EPUB。

**中期（3–6 个月）：**
- **混合检索**：向量检索 + BM25 关键词检索融合。纯向量检索对精确匹配
  （比如具体的数字、人名、专有名词）不敏感，混合检索能补上这个短板；
- **知识库分组**：让用户把文献按课题分组，提问时可指定检索范围；
- **多模态**：论文里的图表是重要信息，目前完全没有利用。

**长期：**
- 引用图谱：把文献之间的引用关系可视化；
- 协作知识库：课题组共享，带细粒度权限；
- 私有化部署方案：模型、向量库、数据库全部本地化，满足数据不出内网的场景。

# 附录　问答预案

以下是预判可能被问到的问题及回答要点。

## Q1：为什么不直接用 LangChain 现成的 RAG 链？

我们确实用了 LangChain 的设计思想，但没有直接套用它的 Chain 抽象。原因有三：

第一，**可控性**。RAG 的每个环节我们都有定制需求——按页判定扫描版 PDF、
三级边界切分、五要素 Metadata、三级超时降级。这些用现成 Chain 都要绕。

第二，**可调试性**。链路封装得越深，出问题时越难定位。我们这次发现的
7 个缺陷里，有 4 个是在真实模型联调时暴露的，能快速定位的前提是
每个环节都是我们自己写的、能直接打断点的。

第三，**依赖体积**。LangChain 的依赖树很重，而我们真正需要的只是
几个 HTTP 调用和提示词模板。

## Q2：向量库为什么选 Chroma？数据量大了怎么办？

Chroma 在本项目的数据规模下是最优解——嵌入式、免运维、本地持久化。

数据量涨上来的迁移路径已经铺好了：所有向量操作都在 `BaseVectorStore`
接口后面，新增一个 Milvus 或 Qdrant 的实现类即可，上层代码零改动。
这个抽象不是纸上谈兵——我们已经用它写了第二个实现（`LocalVectorStore`），
证明了接口的可行性。

## Q3：怎么保证回答一定不出现幻觉？

**不能保证「一定」。** 任何声称能 100% 消除幻觉的说法都是不诚实的。

我们做的是三层遏制：
第一，提示词严格约束「只依据背景资料作答」；
第二，明确要求「资料不足时回答『根据现有资料无法回答该问题』」；
第三，也是最关键的——**引用溯源让每一句话都可验证**。

第三层是本质性的。前两层降低出错概率，第三层让出错**可被发现**。
在严肃场景里，可发现比低概率更重要。

## Q4：如果两篇文献的结论互相矛盾，系统怎么处理？

当前的处理是：两段矛盾的内容都会被检索出来，一起送给模型。
模型通常会在回答中呈现两种观点并分别标注引用，用户能看到分歧的存在。

但我们**没有**做主动的矛盾检测和提示。这是一个已知的、有价值的改进方向——
理想的行为是系统主动提示「检索到的资料中存在冲突结论」。

## Q5：API Key 用 AES 加密，那加密密钥本身存在哪？

存在环境变量 `CONFIG_ENCRYPTION_KEY` 里，不入库、不进代码仓库。

这是一个经典的密钥管理递归问题，标准答案是把根密钥交给专门的密钥管理服务
（云厂商 KMS、HashiCorp Vault）。当前实现用环境变量，
对本项目的部署场景是合适的，也是最常见的做法。

需要提醒的是：**这个密钥必须备份**。丢了之后所有已存的 API Key 都解不开，
只能在后台重新填一遍。这一条我们在 README 的上线检查清单里专门标注了。

## Q6：为什么登录失败要区分「邮箱未注册」和「密码错误」？这不是安全隐患吗？

是的，这会带来邮箱枚举的风险。这是一个**明确的权衡**：

本系统定位是内部或小范围使用的学术工具，用户量有限，
明确的错误提示能大幅减少用户困惑和支持成本。需求文档也明确要求了这一点。

如果要对公网开放，这一条应该改成统一的「邮箱或密码错误」，
并加上登录失败次数限制。改动很小，就在 `auth.py` 里两行。

## Q7：那 7 个缺陷，你觉得怎样才能提前发现？

坦率说，**有 3 个是无法通过写更多单元测试提前发现的**——
它们是前端状态时序、CSS 渲染、真实模型行为，本质上超出了单元测试的能力边界。

能改进的是**流程**：把「浏览器实测」和「真实依赖联调」作为交付的**必经环节**，
而不是可选项。我们已经把浏览器实测固化成了 `npm run e2e` 脚本，
每次前端改动后跑一遍。

真实模型联调目前还是手工的，下一步计划做一个「配置自检」功能——
管理员保存配置后，系统自动用当前配置跑一次完整的探测调用，
把每个环节的成败和耗时直接反馈在界面上。这样配错模型名这类问题，
在保存的那一刻就能被发现，而不是潜伏到用户提问时。

## Q8：扫描版 PDF 的 OCR 效果如何？

需要坦白说明：**当前演示环境没有安装 OCR 引擎**，所以扫描版 PDF 会被
标记为失败，并给出明确提示。这是设计好的降级行为，不是崩溃。

安装 PaddleOCR 之后即可支持，代码路径是完整的、已实现的。
效果取决于扫描件质量——300 DPI 以上的清晰扫描件，中文识别率通常在 95% 以上；
低分辨率或有污渍的扫描件会明显下降，这类失败会进入管理后台的失败队列。

需求文档给的 SLA 是「100 页以内扫描件 120 秒以内」，这个指标需要在装好
OCR 引擎的环境上实测验证，目前尚未验证。

## Q9：项目的代码量和工作量大概是多少？

95 个文件纳入版本管理，其中后端 51 个、前端 38 个、文档 4 个。
后端约 4000 行 Python，前端约 3500 行 TypeScript/TSX，
文档（需求、接口、DDL、变更记录、README、本讲稿）约 3000 行 Markdown。

## Q10：如果现在让你重做一遍，你会改什么？

三件事：

**第一，更早接真实模型。** 我们在 Mock 模式下做完了所有功能才接真实 API，
结果一接就暴露 4 个问题。如果在开发早期就用真实模型跑通一条最小链路，
`max_tokens`、推理模型延迟这些问题会早很多被发现。

**第二，更早用浏览器验证。** 同理。首轮提问回答不显示这种缺陷，
如果开发过程中每完成一个页面就实际点一遍，当天就能发现。

**第三，把配置自检做进 MVP。** 一个依赖大量外部服务配置的系统，
「配置是否正确」应该是可以一键验证的，而不是靠出问题之后去翻日志。
