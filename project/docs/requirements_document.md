## 1. 项目背景

在当今信息爆炸的时代，学术研究者面临着海量非结构化文本资料。传统的关键词检索方式难以理解查询的语义内涵，导致结果冗杂、相关性低，大量时间被耗费在筛选与验证上，而非真正的思考与创新。

大语言模型（LLM）技术的发展为自然语言处理带来了革命性变化，但其固有局限同样明显：
- **知识滞后性**：模型训练数据存在截止日期，无法覆盖最新研究成果；
- **幻觉问题**：模型可能生成看似合理但不准确或虚构的内容；
- **领域局限**：无法有效处理私有领域知识、内部资料与前沿学科内容。

**检索增强生成（RAG）** 技术架构的成熟为上述问题提供了关键方案。RAG 将外部知识库的实时检索与 LLM 的生成能力相结合，确保回答的事实准确性、可追溯性与时效性。

本项目旨在融合 RAG 技术与 LLM 能力，构建一个面向学术研究的智能知识引擎，帮助研究者提升文献调研与论文写作效率。项目的技术框架具备良好的可扩展性，未来可迁移至企业知识管理、法律案例检索、医疗辅助诊断、政府公文分析等多个垂直领域。

## 2. 项目目标

### 2.1 核心目标

开发一套基于大语言模型与检索增强生成技术的 Web 学术辅助工具，允许用户上传专业文献资料，通过语义检索与 LLM 生成相结合的方式，获得精准、可溯源的学术问答服务。

### 2.2 具体目标

- **提升检索效率**：利用文本向量化与语义匹配技术，替代传统关键词检索，从海量文献中快速定位最相关的知识片段。
- **消除幻觉**：通过 RAG 架构与大语言模型的系统提示词引导，确保模型回答严格基于检索到的权威文本片段，遏制编造信息。
- **精确可追溯**：每个回答均在文末标注引用的具体来源文档名称与段落，并支持前端直接定位和展开原始上下文。
- **多端友好与易用性**：提供简洁的 Web 交互界面，支持多轮对话、对话历史搜索与标题自定义，开箱即用。

## 4. 功能需求

### 4.1 用户与角色系统

#### 4.1.1 注册与登录

*   **普通用户注册**：
    *   输入邮箱与密码完成注册。
    *   **邮箱规则**：验证主流邮箱后缀（`@outlook.com`, `@qq.com`, `@gmail.com`, `@163.com` 等），格式不符时前端与后端拒绝并提示，无需发送验证码。
    *   **密码规则**：不少于 6 位的任意字符组合。
*   **登录**：
    *   用户输入邮箱与密码进行登录。
    *   后端验证邮箱存在且密码哈希（bcrypt）匹配，登录成功后返回 JWT。
    *   登录失败时给出明确的提示（"邮箱未注册" 或 "密码错误"）。
*   **会话管理**：
    *   使用基于 JWT 的无状态 Token 管理。
    *   默认有效期设定为 7 天。过期后需重新登录。

#### 4.1.2 密码重置/找回

*   **找回密码机制**：
    *   提供"忘记密码"入口，用户输入注册邮箱。
    *   **频率限制 [M-4]**：同一邮箱 10 分钟内只允许提交 1 次重置申请。若该邮箱已有未处理的申请，后端拒绝并返回 400，提示"您已有待处理的申请，请联系管理员或 10 分钟后重试"。
    *   系统将申请记录至 `password_reset_requests` 表，管理员在后台生成临时密码并标记已处理后，手动转交给该用户。
    *   用户使用临时密码首次登录后须立即修改密码；密码修改完成后，系统将 `users.token_version` 字段自增 1，使该用户此前颁发的所有 JWT Token 立即失效。
*   **JWT 主动失效机制 (token_version) [S-2]**：
    *   JWT Payload 中须包含颁发时的 `token_version` 值。
    *   后端验证 JWT 时，从数据库读取 `users.token_version`；若 Token 携带的版本号小于当前值，则拒绝并返回 `401 Unauthorized`，强制重新登录。
    *   触发 `token_version +1` 的场景：管理员重置用户密码、用户自行修改密码。

#### 4.1.3 角色权限模型 (RBAC)

系统包含两种基本角色：

| 角色 | 权限范围 |
|------|----------|
| **普通用户 (User)** | 上传个人文档、管理个人知识库、多轮学术问答、查看并重命名个人历史对话。 |
| **系统管理员 (Admin)** | 包含普通用户的所有权限；可进入管理后台；管理系统用户；配置系统参数（如默认大模型 API、云端 Rerank Key、动态切片参数）；查看系统运行日志和调用统计。 |

### 4.2 知识库管理与隔离

#### 4.2.1 物理与逻辑隔离

*   **文件存储隔离**：
    *   用户上传的原始文件统一保存在服务器本地目录（如 `/data/uploads/{user_id}/` ）。
    *   目录结构按照 `user_id` 进行层级划分，保障数据安全。
*   **向量库物理隔离**：
    *   为了彻底杜绝跨用户数据泄露风险，**为每个用户在 Chroma 中创建独立的 Collection**，Collection 命名规则为 `col_user_{user_id}`。
    *   用户仅能对其名下了 Collection 进行检索和修改。

#### 4.2.2 文档上传与限制

*   **上传限制**：
    *   单个文件最大大小限制为 **50MB**。
    *   单次批量上传最大文件数量为 **10个**。
    *   支持的格式：PDF、DOCX、TXT、Markdown。
*   **扫描版 PDF OCR 解析**：
    *   文件解析器在处理 PDF 时，应首选尝试提取文本。若检测到页面文本内容为空，或提取文本密度极低，则判定为“扫描版 PDF”。
    *   启动内置 OCR 引擎，按页将 PDF 渲染为图像，使用 OCR (如 PaddleOCR) 逐页识别并将提取出的文本按页合并，然后传入切块模块。

#### 4.2.3 动态文档切分 (Chunking)

*   **切分参数配置**：
    *   具体切片大小（Chunk Size）与重叠大小（Overlap）不固定，初期定义为后台系统参数（如默认 Chunk Size=600, Overlap=60），由管理员在后台动态微调测试。
*   **向量化入库 [S-3]**：
    *   调用 `Qwen/Qwen3-Embedding-8B` 模型对文本块进行向量化。
    *   **向量片段 Metadata 规范（强制要求）**：每个向量切片写入 Chroma 时，必须在 Metadata 中包含以下字段。若缺失，删除文档时将无法定位对应向量，导致向量库持续积累垃圾数据：
        - `doc_id`：文档唯一 ID（对应 `documents.id`）
        - `user_id`：所属用户 ID
        - `file_name`：原始文件名
        - `page`：所在页码（PDF 有值；TXT/Markdown 为 null）
        - `chunk_index`：切片序号（0-based）
    *   删除文档时，后端通过 `collection.delete(where={"doc_id": "<doc_id>"})` 一次性清除该文档的全部向量片段。

#### 4.2.4 知识库概览与维护

*   用户可在 Web 界面查看已上传的文档列表（含文件名、文件大小、解析状态、上传时间）。
*   **文档状态**：包括 `解析中`、`OCR识别中`、`向量化中`、`已就绪`、`失败`。
*   **删除文档**：
    *   用户可以点击删除文档，后端同步删除本地物理文件、MySQL 中的文档元数据以及 Chroma 向量库中对应文档 ID 的所有向量片段。

### 4.3 智能问答与 RAG 引擎

#### 4.3.1 语义检索与精排

1.  **密集检索 (Dense Retrieval)**：用户输入问题后，系统使用相同的 `Qwen/Qwen3-Embedding-8B` 模型对问题进行向量化，在用户的专属 Chroma Collection 中检索出 Top-N (如 N=20) 的相关文本片段。
2.  **重排 (Reranking)**：将问题与这 20 个候选片段拼接，调用**云端 Rerank API** (例如 Cohere Rerank 或 阿里云百炼 Rerank API) 进行精排，筛选出相关度最高的前 Top-K (如 K=5) 片段作为最终的背景资料。

#### 4.3.2 答案生成控制

*   **Prompt 约束**：
    *   将精排得到的文本片段与系统提示词（System Prompt）进行拼接，送入大模型（默认：`deepseek-ai/DeepSeek-V4-Flash`）。
    *   **幻觉遏制规则**：大模型必须严格根据所给的背景资料进行作答。如果背景资料中没有回答问题所需的信息，模型必须直接回答“**根据现有资料无法回答该问题**”，且不能添加任何编造或猜测的内容。
*   **流式输出**：问答接口应支持 Server-Sent Events (SSE)，将 LLM 生成的答案以流式（Stream）形式实时呈现在前端。

#### 4.3.3 多轮对话上下文

*   支持连续多轮追问。
*   每次提问时，将前置的对话历史（历史轮数上限由管理员在后台配置）合并后，由 LLM 进行 **Query Rewrite（问题改写）**，将追问改写为包含上下文的独立检索 Query，再进行向量检索。
*   **超时与降级策略 [M-6]**：
    *   Query Rewrite 超时（> 3s）：降级为直接使用用户原始问题进行向量检索，不中断 SSE 连接。
    *   云端 Rerank API 超时（> 3s）：跳过 Rerank，直接使用向量检索 Top-K 结果送入 LLM；SSE `done` 帧的 `warnings` 字段携带 `"rerank_timeout"` 告知前端。
    *   LLM 生成超时（> 30s）：SSE 推送 `event: error` 事件后关闭连接，提示用户重试。

#### 4.3.4 引用溯源呈现

*   **格式要求**：模型生成的答案中需要包含数字标记（如 `[1]`，`[2]`），在答案末尾提供对应的引用列表。
*   **展示内容 [I-3]**：引用列表须清晰标明来源。PDF 文档标注 `第 X 页`；TXT/Markdown 等无页码文档标注 `第 N 个片段`（使用 `chunk_index`）。每条引用包含 `doc_name`、`page`（可选/null）、`chunk_index`、`snippet` 四个字段。
*   **交互展开**：前端支持点击引用标记或下方引用卡片，弹窗或展开抽屉以显示对应的原文段落全文。

#### 4.3.5 纯模型对话模式 (`enable_rag=false`) [S-4]

当请求体中 `enable_rag=false` 时，RAG 流程的向量检索和 Rerank 步骤均跳过，具体行为如下：

*   **历史上下文传递**：仍读取并传递当前会话的历史消息（`chat_messages`），保持多轮连贯性；历史轮数上限受后台参数约束。
*   **消息持久化**：用户提问与 LLM 回答正常写入 `chat_messages` 表；`citations` 字段值为 `null`。
*   **SSE 事件序列**：仅推送 `event: chunk`（增量文本）和 `event: done` 两类事件；`done` 帧中 `citations` 为 `[]`，`warnings` 为 `[]`。

### 4.4 对话历史管理

#### 4.4.1 历史记录保存

*   每轮对话交互（用户提问内容、系统回答内容、引用的文档信息及具体文本）均自动持久化存入关系型数据库。
*   所有的历史会话按用户进行权限隔离，无法越权查看。

#### 4.4.2 标题自动生成与修改

*   **标题自动生成**：在新对话的首次提问后，系统异步调用大模型，基于该问题生成一个简短（15字以内）的摘要，作为该对话的“会话标题”。
*   **手动重命名**：用户可点击会话旁边的“编辑”图标，手动修改会话标题。
*   **历史查询**：
    *   前端侧边栏展示历史会话列表，支持按创建时间倒序排列。
    *   支持输入关键词，对历史会话标题进行模糊搜索。

#### 4.4.3 会话管理

*   用户可以点击历史会话卡片，快速载入并展示之前的聊天记录，并可以继续在当前上下文中提问。
*   支持删除整个会话，删除后该会话在 MySQL 中标记为已删除（或物理删除，且级联删除所有关联的消息记录）。

### 4.5 系统管理 (Admin 后台)

系统管理员可以通过专属的管理页面进行如下操作：

1.  **用户管理**：
    *   查看所有已注册用户列表（注册时间、最后登录时间、用户角色、上传文档数量）。
    *   可以重置用户密码、修改用户角色（User <-> Admin）或禁用/启用用户。
2.  **系统配置**：
    *   大模型配置：修改 OpenAI 兼容 API 的 Base URL、API Key、默认 Model 名字。
    *   Rerank 配置：修改云端 Rerank API 终结点、API Key、Rerank Top-K 等参数。

3.  **运行监控**：
    *   查看系统调用次数、大模型 Token 消耗量、OCR 处理失败队列。

## 5. 非功能需求

### 5.1 性能指标

*   **检索响应时延**：语义检索 + 云端 Rerank（不含大模型生成）端到端响应时间应在 **< 2s**。
*   **并发性能**：支持至少 **10 个** 并发用户同时在线提问，不出现请求超时或服务崩溃。
*   **文档解析与向量化耗时**：
    *   对于普通可读式电子版 PDF/DOCX (100 页以内)，从上传到向量化就绪时间 **< 30s**。
    *   对于扫描版 PDF (需要启用 OCR)，耗时会增加，SLA 指标定义为：100页以内扫描版文档处理时间 **< 120s**。

### 5.2 安全性

*   **数据隔离安全**：
    *   Chroma 的 Collection 实行单用户单 Collection 机制。
    *   MySQL 数据表中必须包含 `user_id` 过滤，确保 API 层拦截越权查询（水平权限越权防御）。
*   **密码安全**：
    *   用户密码在数据库中必须采用高强度的 `bcrypt` 单向哈希算法进行加密保存，拒绝明文存储。
*   **通信安全**：
    *   生产环境下全站使用 HTTPS 加密，包括 API 调用与流式推送。
*   **API 密钥管理 [S-1]**：
    *   所有的 API Key（大模型、Rerank 等）均必须保存在后端环境变量或 `system_configs` 数据库表中，禁止暴露在前端代码里。
    *   **静态加密（At-Rest Encryption）**：API Key 写入 `system_configs` 表之前须经服务端 **AES-256** 对称加密，仅存储密文；后端在运行时于内存中解密使用。**任何 HTTP 响应均不得返回 Key 明文**；`GET /api/v1/admin/configs` 接口中所有 API Key 字段一律以脱敏掩码（如 `sk-****xxxx`）返回。

### 5.3 可扩展性

*   **模型层抽象**：底层采用 LangChain 的 ChatOpenAI 接口或统一封装的 Adapter。管理员可在不修改代码的前提下，通过后台直接切换至 DeepSeek、通义千问、OpenAI 或 本地自建 LLM。
*   **向量库抽象**：Chroma 向量库操作封装为独立服务，方便未来系统需要扩展为分布式向量数据库 (如 Milvus、Qdrant) 时快速迁移。

### 5.4 可用性

*   **响应式布局**：前端基于 TailwindCSS 自动适配宽屏显示器、笔记本电脑以及手机等移动终端浏览器。
*   **多语言与友好交互**：界面采用纯中文，所有报错信息应转化为用户易懂的提示语。
*   **加载状态反馈**：文档上传、解析中、AI 生成中等操作，均必须提供明确的骨架屏、旋转 Loading 指示器或百分比进度条。

## 8. 核心 API 接口设计

所有的 API 请求头均需携带：`Authorization: Bearer {JWT_TOKEN}` (管理后台接口另需具备 Admin 权限)。

### 8.1 用户认证模块
*   `POST /api/auth/register` : 用户注册。
*   `POST /api/auth/login` : 用户登录，返回 Token。
*   `POST /api/auth/forgot-password` : 提交邮箱申请重置。
*   `POST /api/auth/reset-password` : 使用验证凭证重置密码。

### 8.2 知识库管理模块
*   `POST /api/docs/upload` : 多文档上传（Multipart Form-Data），最大 50MB/文件，单次最多 10 个。
*   `GET /api/docs/list` : 获取当前用户的文档列表（分页）。
*   `DELETE /api/docs/{doc_id}` : 删除指定文档，同步清理 MySQL 元数据、物理文件以及该用户 Chroma Collection 中的对应向量。

### 8.3 智能问答模块
*   `POST /api/chat/session` : 创建新会话。
*   `PUT /api/chat/session/{session_id}` : 修改会话标题。
*   `GET /api/chat/sessions` : 获取当前用户的所有历史会话。
*   `DELETE /api/chat/session/{session_id}` : 删除会话（逻辑/物理删除）。
*   `POST /api/chat/query` : 发送提问接口，支持流式 SSE。
    *   请求体：`{ "session_id": "...", "query": "..." }`
    *   返回：流式输出生成的文本 + 最终附带的 `citations` 结构数据。

### 8.4 管理员后台模块
*   `GET /api/v1/admin/users` : 获取所有用户列表（含最后登录时间、文档数量）。
*   `PUT /api/v1/admin/users/{user_id}/role-status` : 变更用户角色或启用/禁用账号。
*   `PUT /api/v1/admin/users/{user_id}/reset-password` : 重置用户密码并返回随机临时密码（同步触发 `token_version +1`）。
*   `GET /api/v1/admin/reset-requests` : 查看待处理的密码重置申请列表。
*   `GET /api/v1/admin/configs` : 获取系统全局配置参数（LLM、Rerank、Embedding、切片），**API Key 脱敏返回**。
*   `PUT /api/v1/admin/configs` : 保存/更新全局配置参数，API Key 由后端 AES-256 加密后写入数据库。
*   `GET /api/v1/admin/stats` : 获取运行监控数据（调用次数、Token 消耗、失败率、OCR 失败队列）。

## 11. 附录

### 附录 A：系统提示词设计

系统提示词（System Prompt）作为引导 LLM 行为的核心模板，将用于每次问答调用：

```text
你是一个专业的学术知识助手。请严格依据以下提供的背景资料来回答问题。如果资料中没有足够信息来回答问题，请直接说明“根据现有资料无法回答该问题”，切勿编造信息。你的回答应简洁、专业，并可进行合理的学术引用。在回答中引用背景资料时，必须在对应位置打上数字引用标记（例如 [1]、[2]）。

【背景资料】
{retrieved_contexts}

请在回答末尾，按以下格式标注引用的来源文档名称与具体段落内容：
---
参考来源：
[1] 《文档名A》—— 第 X 页/段落：段落核心摘要或内容
[2] 《文档名B》—— 第 Y 页/段落：段落核心摘要或内容
```

### 附录 B：常见术语表

| 术语 | 说明 |
|------|------|
| **LLM** | Large Language Model，大语言模型，基于海量文本训练的深度学习模型 |
| **RAG** | Retrieval-Augmented Generation，检索增强生成，结合检索与生成的 AI 框架 |
| **Embedding** | 嵌入/向量化，将文本转换为高维向量表示的过程 |
| **Chroma** | 开源嵌入式向量数据库，本系统使用其单用户单 Collection 隔离机制 |
| **LangChain** | LLM 应用编排框架，提供 Prompt 管理、链式调用等能力 |
| **Dense Retrieval** | 密集检索，通过向量相似度计算进行语义匹配 |
| **Rerank** | 重排技术，利用深度交互模型对初筛得到的文档片段进行二次高精度排序 |
| **OCR** | Optical Character Recognition，光学字符识别，本系统用于从扫描 PDF 提取文本 |
